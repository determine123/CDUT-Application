# 把项目变成能被理解的能力证据

> 通用方法，整理于 2026-10-03；具体校内政策另行核查。

一个作品至少回答：问题是什么，输入和输出是什么，自己负责什么，怎样知道结果可靠。

## 最小交付清单
README 写背景、安装、运行、示例、数据来源和限制；依赖环境可重复；代码结构能看出主要流程。把输入样例、预期输出和必要检查一起提供，别人不需要猜你如何运行。

## 有意义的比较
建立简单基线，再说明改动和结果。性能比较注明硬件、数据、配置与测量方法；质量评估说明样本和局限。无证据就不写“提升百分之多少”。

## 项目深度
记录失败方案及为何放弃，展示问题定位与验证。小项目可以深入，大项目也可能只是拼接工具，规模不是唯一指标。

## 面试前
沿输入到输出走一次流程，解释关键选择与替代方案。团队分工清楚，原有开源代码保留许可；密钥与私有数据移出公开仓库。没有许可时只展示脱敏说明，不上传公司代码。

AI 辅助的部分可以透明说明，个人能力体现在理解、判断、验证和维护，不把生成代码的体量当成果。

## 为一个项目准备一次可复现演示

先选择一个最能解释自己贡献的场景，而不是展示所有菜单。准备合法可公开的输入、运行命令、预期行为，以及一项会失败的输入。演示前在新的目录或环境按 README 运行一次，记录缺失的依赖、路径和配置。

现场无法联网或没有设备时，准备带版本和日期的演示记录。录像可以帮助展示，但不能代替对流程的理解；别人问到某个结果时，应能解释输入、处理步骤和验证方法。私有项目只展示获准公开的内容，不为演示复制内部数据。

## 从一句项目描述追到证据

给简历中的每个主要说法补一个依据：

- “完成某功能”：指出代码位置、可执行示例及适用输入。
- “修复某问题”：保留触发条件、修复前的失败、修复后的检查，并说明验证范围。
- “改善性能”：保留同条件下的基线、测量记录和配置，不能将不同设备或不同任务直接比较。
- “与团队协作”：说明自己负责的模块、接口或 review，区分个人动作与共同结果。
- “用户实际使用”：说明可确认的部署或使用记录；只有本地演示时就写本地验证。

没有证据的说法先缩小到能确认的范围。测试通过只能证明所覆盖的行为；单个样例成功不能推出所有输入可靠。

## 给项目 README 增加一个证据段落

以下模板是待填写结构，不能直接作为个人成果声明。

```markdown
## 本人完成与验证
- 基于什么：[原项目、课程任务或自行实现；注明来源]
- 本人负责：[具体模块和动作]
- 代表改动：[提交或代码位置；私有内容用获准公开的说明]
- 验证场景：[输入、环境、命令、预期行为]
- 实际结果：[完成、失败或尚未验证的范围]
- 已知限制：[适用条件、依赖、不能覆盖的情况]
```

使用开源项目时，可以把“复现运行”“理解并调整配置”“新增功能”“独立设计”分开说明。原作者的实现保留来源，自己的修改说明位置。使用 AI 辅助时，讲清由自己作出的选择、检查和后续维护。

## 面试前的三种追问

试着不用 README 回答：输入异常时在哪里处理？换一种方案会有什么代价？上次失败是怎样定位的？答不清楚时回到代码或实验记录核对，不临时编造理由。把确实发现的缺陷修复并补充必要检查，比临时增加陌生功能更能加深理解。
