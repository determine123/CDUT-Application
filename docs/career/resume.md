# 简历与作品集

> 整理：2026-10-03。通用建议、个人经历与政策分开阅读；当年官方文件优先。

让读者知道你解决过什么问题。教育经历如实写正式专业、年份与学位，不因转专业而制造多学位误解。

项目围绕问题、个人动作和验证结果。数字来自记录，不把团队总成果全部算作自己。没有提升数字时描述完成范围和局限即可。

作品集选少量能运行的项目，写清安装、运行、数据来源、许可证和个人职责。公开前查密钥、私人文件与未授权代码。

逐项检查简历名词能否解释、结果能否复现、协作能否说明分工。理解不足就补课或删掉，不依赖临场编造。个人完整简历无需上传手册。

## 先挑项目，再改写句子

按岗位要求选择少量最相关的经历。每个项目至少能回答背景、本人工作和验证范围，避免几个项目都只写“使用某框架搭建”。项目越小，越可以把一个具体问题的定位和解决讲清楚。

可以按“在什么约束下，为解决什么问题，完成什么动作，用什么方式验证”组织要点。没有业务规模或性能数据时，写实际交付的功能与边界即可；不要为使句子有数字而估算无法核对的提升比例。

## 描述中容易混淆的阶段

完成本地演示、部署测试环境、公开发布和有人实际使用是不同状态。论文投稿、接收和发表也分别表述；项目参加比赛与获奖不能混用。把确实发生的阶段写清楚，读者才知道结果的含义。

团队经历写本人动作，必要时注明参与范围。基于教程、开源仓库或 AI 辅助完成的项目，说明自己新增或验证的部分，不把原项目全量代码当作独立开发成果。

## 投递前的一次检查

- 教育经历与正式专业、年份和学位一致，转专业或方向选择没有被写成额外学位。
- 每个项目要点都有自己可以说明的依据，技术名词与实际工作对应。
- 链接可打开，示例能运行，公开仓库不需要私人路径或密钥才能理解。
- PDF 文字可选取，链接有效，导出后没有错位或丢字；文件名便于识别。
- 联系方式仅用于自己选择的投递渠道，公开作品集使用愿意公开的联系方式。

可以请同学只看简历复述“你做过什么”，再根据误解调整表达。复述检查的是清晰度，不代替对经历真实性和岗位要求的核对。后续用[项目证据](project-proof.md)和[面试准备](interview.md)检验自己是否能展开解释。
