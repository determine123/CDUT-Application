# 投稿与维护

欢迎不同专业、年级和去向，成功、失败与转向同样有价值。

## 网页投稿
1. 登录 GitHub，在个人 fork 编辑对应 Markdown 或新增文件。
2. 新增页面同时加入 mkdocs.yml 的 nav，文件名用小写英文短横线。
3. 创建 PR 到 main，说明来源、适用背景与改动。
4. 维护者检查事实、隐私、许可、链接和构建后决定合并。

无需安装工具即可编辑。不熟悉 Git 可在 issue 提交自己授权公开的文字，不上传证件和成绩单原件。

纠错注明页面、段落、时间和证据。保留不同背景，不发布可识别个人的未经核实指控。拒绝伪造案例、广告、代写代考与侵权转载。

投稿原创文字表示有权公开并按 CC BY 4.0 授权。第三方材料另行声明，维护者应保留原作者署名。

## 第一次投稿从哪里开始

在[投稿模板](templates.md)选择通用、考研或推免结构；不必回答每个问题。一篇文章先把一次关键选择、本人行动和结果阶段讲清楚，比堆满成绩与学校名称更有参考价值。希望先回答问题再整理，可使用[访谈提纲](interview.md)。

已有文章的纠错应注明原文位置、错误原因和来源。暂时无法核实的经历可以讨论，但不能作为已确认案例收录。读者只能提供“我认识某位同学”的信息时，先记为待本人投稿，不据此代写完整经历。

## 匿名与授权确认

提交 issue 和 PR 的文字、附件、账号及历史通常可以公开查看。希望隐藏 GitHub 身份时，不要先用本人账号发出敏感内容再请求匿名；仅使用自己愿意公开的文字与投稿身份。文章使用昵称并不意味着提交记录也匿名。

作者可要求省略精确成绩、院系、导师或年份；维护者应确认余下信息的组合是否仍容易识别个人。第三人代投稿应在 PR 说明“已由本人核对并授权公开”，不要求提供身份证或聊天截图证明身份。

发布前明确：署名方式、允许公开的版本、原创部分按 CC BY 4.0 授权、第三方材料的处理方式。开放许可可能允许他人继续使用已获得授权的副本，公开前应理解这一点，参见[许可说明](https://creativecommons.org/licenses/by/4.0/deed.zh-hans)。

## 维护者合并清单

1. 核对这是真实经历、方法建议还是政策说明；为不同性质保留相应的来源和适用范围。
2. 核对本科推荐资格、接收意向、拟录取、正式录取等阶段，避免把待确认结果写成最终结果。
3. 检查作者署名、授权、个人与第三方隐私，不把转载素材自动纳入本项目许可。
4. 保留失败、转向和不同背景；删去无法核实的指控、广告与对个别经历的过度概括。
5. 检查新增页面的导航与内部链接，通过严格构建后再合并。

发布后需更正时，说明页面和段落、希望修改的公开内容及原因。维护者可以修改当前页面，但不能保证已公开的历史提交、搜索缓存或第三方副本同步消失；不要再次上传原始敏感材料。
